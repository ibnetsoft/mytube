# AIR Worker — 자원 우선순위 및 스케줄 정책

- 상태: **설계안 / CTO 승인 대기**
- 관련 문서: [ARCHITECTURE](./AIR_WORKER_ARCHITECTURE.md), [JOB_PROTOCOL](./AIR_WORKER_JOB_PROTOCOL.md)

## 1. 기본 우선순위 (지시사항 값 그대로 채택)

| 작업 | priority |
|---|---|
| 사용자 직접 요청 렌더링 | 100 |
| 예약된 영상 렌더링 | 80 |
| 이미지 렌더링 | 70 |
| 주제 생성 (`topic_generate`) | 40 |
| Hermes 시장 조사 (`topic_research`) | 20 |
| 정기 유지보수 (`health_check` 등) | 10 |

Job Scheduler(§PROCESS_MODEL §1)는 큐에서 항상 **priority 내림차순**으로 다음 작업을
선택한다. 동일 priority 내에서는 `created_at` 오름차순(FIFO) — Stage 1에서 확인한 기존
`remote_render_queue`의 "oldest first" 관례와 일치시킨다.

## 2. 렌더링 작업이 시작될 때

- **Hermes 신규 작업 시작 금지**: Job Scheduler가 `render_*` job을 Render Worker Process에
  배정하는 순간, Hermes Worker Process에는 새 `topic_*` job을 배정하지 않는다(이미 실행
  중인 게 있으면 §아래 "안전한 체크포인트" 참고).
- **실행 중인 Hermes 작업은 안전한 체크포인트에서 일시 정지 가능하도록 설계**: Hermes
  Worker Process는 장시간 작업(AIR-0226 PoC 실측 86초) 중간에 "여기까지 완료, 여기서부터
  재개 가능"한 지점을 잡아야 한다. 구체적으로: `topic_research`(외부 LLM 호출 자체)는 원자적
  단일 요청이라 중간에 끊을 수 없으므로, **체크포인트는 "LLM 호출 완료 후 결과 저장 직전"과
  "결과 저장 후 다음 카테고리로 넘어가기 전" 사이**로 잡는다 — 이미 시작된 LLM 호출 1건은
  끝까지 완료시키고, 그 다음 배치를 시작하지 않는 방식(§JOB_PROTOCOL의 `paused` 상태가 이
  지점에서 쓰인다).
- **브라우저 자동화 프로세스 수 제한**: Hermes가 시장조사 과정에서 브라우저 자동화(예:
  벤치마크 채널 스크래핑)를 쓴다면, 렌더링 중엔 그 프로세스 개수 상한을 낮춘다(§10 기본값
  "최대 1개"가 평시 기준, 렌더링 중엔 0개로 낮추는 것을 제안).
- **CPU와 RAM 상한 설정**: Hermes Worker Process에 OS 레벨 리소스 제한(Windows Job Object
  또는 프로세스 우선순위 클래스 하향)을 걸어, 렌더링이 CPU를 최우선으로 쓸 수 있게 한다 —
  Stage 1에서 확인했듯 렌더링은 CPU 소프트웨어 인코딩(`libx264`)이 전부라 **CPU 경쟁이
  실제로 존재하는 유일한 자원 축**이다(GPU는 애초에 아무도 안 씀, §ARCHITECTURE §5 표 참고).

## 3. 렌더링 큐가 비어 있을 때

- Hermes 작업 재개 (§2에서 일시정지된 게 있으면)
- 예약된 시장 조사 실행
- 주제 후보 배치 생성

## 4. 초기 기본값 (지시사항 10단계 그대로)

```
렌더링 큐 있으면 렌더링 우선
Hermes 시장조사는 렌더링 큐 빌 때만 실행
Hermes 동시 작업 기본 1개
브라우저 자동화 최대 1개 (렌더링 중엔 §2에 따라 0개로 하향 검토)
일일 카테고리별 조사 횟수 기본 1회 (AIR-0226 §ARCHITECTURE §8과 정합 — 이미 그쪽 문서에서 제안한 값과 일치시킴)
렌더링 시작 시 Hermes 신규 작업 중단
```

## 5. GPU/VRAM 리소스 정책에 대한 정직한 코멘트

Stage 1에서 확인했듯 **GPU 가속은 현재 코드베이스 어디에도 실제로 연결되어 있지 않다**
(`USE_GPU_RENDER` 플래그가 있지만 아무 인코딩 경로도 이걸 참조하지 않음, 전부 `libx264`
CPU 인코딩). 그럼에도 관리 UI 표시 항목(Stage 8)에 GPU/VRAM이 명시되어 있으므로:

- 스켈레톤 구현(§12)은 GPU/VRAM을 **표시만 하고**(`nvidia-smi` 파싱 또는 WMI 조회로 실제
  하드웨어 존재 여부/사용률만 읽어옴), 그 값을 스케줄링 판단에 실제로 사용하지 않는다.
- 실제 GPU 가속 인코딩(nvenc 등) 도입은 이 Task 범위 밖이며, 도입되면 이 문서의 §2 CPU
  상한 정책에 "GPU 상한"도 대칭적으로 추가해야 한다 — 다음 Task 제안 목록에 후보로 포함.

## 6. 자원 충돌 방지 정책 요약 (완료보고서용)

| 자원 | 충돌 가능성 | 방지책 |
|---|---|---|
| CPU | 있음(렌더 인코딩 vs Hermes 프로세스) | §2 프로세스 우선순위 하향 + 신규 Hermes 작업 중단 |
| RAM | 있음(둘 다 어느 정도 사용) | §2 RAM 상한 |
| GPU/VRAM | **현재 없음**(§5) | 표시만, 실사용 없음 |
| 네트워크 대역폭 | 있음(렌더 결과 업로드 vs Hermes API 호출/브라우저 자동화) | 브라우저 자동화 프로세스 수 제한(§2), 별도 대역폭 쿼터는 이번 범위 밖 |
| 디스크 I/O | 낮음(렌더 임시파일이 지배적, Hermes는 텍스트 위주) | 별도 정책 불필요 |
