## 6. 통합워커 연결에서 발견한 장애 요인

### A. 기본 실행 프로세스에 AE 입모양 수신기가 없음

코드 기준:

- `worker/manager.py`의 `CHILD_SCRIPTS`
- `worker/worker_config.py`의 `PROFILE_CHILD_SCRIPTS`

두 목록에는 `ae_highlight_worker`는 있으나 **`ae_mouth_worker`가 없다**. `ae_highlight_worker`가 입모양 JSX 기능을 import하는 것과 `ae_mouth_job` 큐를 가져오는 것은 다르다.

입모양 큐는 `worker/ae_mouth_worker.py:process_one()`이 `std_project_assets.metadata.kind=ae_mouth_job` 레코드를 직접 조회해 처리한다. 일반 중앙 `worker_jobs` 큐로 전달되는 구조가 아니다.

별도로 이 프로세스를 실행한 Windows 컴퓨터가 있다면 처리할 수 있지만, 그 실행 상태와 설치된 커밋은 이번 세션에서 확인하지 못했다. 저장소의 기본 통합워커만 켜면 자동으로 이 프로세스가 켜진다고 보장할 수 없다.

중앙 `workers` 테이블의 가장 최근 heartbeat는 2026-09-26이었다. 다만 독립 AE 프로세스의 생존 신호가 이 테이블에 반드시 기록되는 것은 아니므로 이 사실만으로 Windows 컴퓨터 전체가 꺼졌다고 단정하지 않는다.

### B. 워커 입력 재검증의 자료 조회가 아직 페이지를 순회하지 않음

`worker/ae_mouth_worker.py`의 `fresh()`는 현재 프로젝트 asset을 한 번의 REST GET으로 조회한다. 이 프로젝트는 접수 직전 활성 자료만 1,265개였으며 원본 영상은 최신순 1,019~1,036번째에 있다.

따라서 웹 접수 입력은 정상이어도, 워커가 다시 읽을 때 원본 영상이 누락되면 `input_matches()`가 false가 되어 정상 작업을 `obsolete`로 잘못 바꿀 수 있다.

앞서 고친 웹 경로(`/submit`, `/reopen`, `/ae-mouth`, 최종 렌더 bundle)와 별도로 **Python 워커 조회도 페이지 처리가 필요하다.** 단순히 대형 limit 하나를 넣거나 검증을 제거하는 방식으로 우회하면 안 된다.

### C. 최종 렌더 연결 스크립트에도 동일 조회 문제

`scripts/std_continue_submission.cjs`도 전체 asset을 단일 조회한다. 현재 상태를 읽거나 `--enqueue`로 검수된 결과를 최종 렌더에 연결할 때 같은 누락이 발생할 수 있다.

이 스크립트는 `loadStdProjectAssets()`를 사용하도록 보완하고, 1,000개 이후에 원본 영상이 있는 프로젝트로 다시 검증해야 한다. 이번 감사에서 `--enqueue`나 검수 승인 명령을 실행하지 않았다.

### D. 자동 완료는 아직 보장되지 않음

입모양 워커는 일반적으로 다음 상태를 사용한다.

```text
queued → processing(discovery) → direction_pending
       → direction_approved → processing(render) → review_pending
       → reviewed → 최종 렌더 큐 등록 → pending/rendering/completed
```

일부 씬은 `needs_review`, 대사 없는 씬은 `skipped`가 될 수 있다. 방향 승인과 결과 검수는 실제 원본·음성·영상 증거를 확인한 뒤 해야 한다. 워커 실행 파일 하나만 켠다고 승인 및 최종 렌더 접수까지 무조건 자동 완료되는 구조가 아니다.

화면의 “후작업과 검수 후 최종 렌더링이 자동으로 진행됩니다”는 이후 연결이 실제 가동될 때의 흐름을 설명한다. 현재 완료 증거는 아니다.

| 최종 렌더 등록 | 이번 작업과 연결된 새로운 render queue ID |
| 전체 완료 | 해당 큐의 completed 및 실제 최종 영상 확인 |
