# AIR-0221A: Emergency Money Path Hotfix

## Goal
Restore two admin money-movement actions that were confirmed dead in production during AIR-0221 audit (see `CONSOLIDATION_PLAN.md` §10.5): "mark withdrawal completed" and "manual referral payout." Both called RPCs that no longer exist in the live database. Emergency scope only — no schema changes, no new RPCs, no referral-model changes.

## Root cause
- `process_withdrawal_commission` — dropped by `migrations/air_0158c_drop_withdrawal_commission_rpc.sql`, but `auth-web/app/api/admin/withdrawals/route.ts:96` still called it.
- `process_referral_payout` — does not exist in the live schema at all (confirmed via PostgREST OpenAPI introspection + direct RPC probe, both returning `404 PGRST202`), despite `auth-web/app/api/admin/settlements/payout/route.ts:29` calling it.
- **Newly discovered while fixing the above**: `increment_usdt_balance`, which the payout fix was initially going to lean on, is *also* broken — its body does `UPDATE profiles SET usdt_balance = ..., updated_at = NOW()`, and `profiles` has no `updated_at` column (confirmed live: `42703 column "updated_at" of relation "profiles" does not exist`).

## Actions taken
- `auth-web/app/api/admin/withdrawals/route.ts`: replaced the `process_withdrawal_commission` RPC call with an inline `processWithdrawalCommission()` function that reproduces the RPC's exact logic via the still-live `calculate_commission` RPC + direct `UPDATE withdrawals` / `INSERT tenant_commission_logs`. State machine (Requested→Approved→Sending→Completed) untouched.
- `auth-web/app/api/admin/settlements/payout/route.ts`: replaced the `process_referral_payout` RPC call with two direct steps: (1) an atomic conditional `UPDATE referral_commissions SET status='paid' WHERE id=X AND status='pending'` (the `status='pending'` guard in the WHERE clause prevents double-payout on retry/race, same protection the RPC's `FOR UPDATE` gave), then (2) a direct read-modify-write on `profiles.usdt_balance` (avoiding `increment_usdt_balance` entirely, since it's also broken). If step 2 fails, step 1 is compensated (reverted back to `pending`) so the commission isn't left stuck "paid" without the balance actually being credited.
- No schema changes. No new RPCs created. No changes to `referral_commissions`/`withdrawals`/`tenant_commission_logs` table shape.

## Verification performed
- `npx tsc --noEmit` — no new errors in either file (pre-existing unrelated errors elsewhere in the repo, confirmed present before this change too).
- `eslint` on both files — clean.
- Live-schema checks against production Supabase (read-only + safe no-op RPC probes, no real rows touched):
  - `calculate_commission` — confirmed live and working (returns clean `user_not_found` for a dummy UUID, not a schema error).
  - `increment_usdt_balance` — confirmed broken (`42703`), which is why the payout route does the balance credit directly instead.
- **Not performed**: true end-to-end test through the deployed admin UI against a real withdrawal/commission row. This route requires an authenticated admin session (`requireAdmin`/`requireSuperAdmin`), which isn't available from this environment, and there's no staging Supabase project — only production. Recommend the CTO/an admin click through both actions once on a real (or deliberately created small test) withdrawal/commission after deploy, as the actual regression test.

Not touched here because this entire code path is already scheduled for deletion in AIR-0221 Stage 1 (`CONSOLIDATION_PLAN.md` §10.2) — fixing a function slated for deletion within days isn't worth the risk.
