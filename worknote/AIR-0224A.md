# AIR-0224A: Production Profile Referral Trigger Hotfix

## Goal
Fix two live production bugs discovered while running AIR-0224 Phase 1 (test account creation): (1) any `UPDATE` on `public.profiles` fails with `42703 record "new" has no field "referrer_id"`, (2) `profiles.referred_by` stays `NULL` even when `user_metadata.referred_by_id` is correctly sent at signup.

## Investigation (read-only; no SQL Editor access in this environment, so done via codebase archaeology + REST-level probing)

### Bug 1 — the `referrer_id` UPDATE failure

Found **three** triggers, all `AFTER UPDATE ON public.profiles`, all committed together in one batch (`b2e8a0ee`, "AIR-0207A Revise Asset Analysis and Matching logic", 2026-07-07) as part of a never-launched Gen 3 admin/risk/habit/analytics feature stack with zero application callers (already established in `CONSOLIDATION_PLAN.md`'s earlier audit):

| Trigger | Function | File |
|---|---|---|
| `trigger_referral_join` | `handle_referral_join()` | `migrations/air_0205_referral_notifications.sql:29-73` |
| `trigger_user_activity_referral` | `handle_user_activity()` | `migrations/air_0206_habit_loop.sql:23-141` |
| `trigger_analytics_referral_join` | `handle_backend_analytics()` | `migrations/air_0207_analytics.sql:25-62` |

Each function unconditionally dereferences `NEW.referrer_id`/`OLD.referrer_id` near the top of its body, before any actual business logic — `profiles.referrer_id` has never existed in this codebase (confirmed: no `ALTER TABLE profiles ADD COLUMN referrer_id` anywhere; the real column is `referred_by`, `auth-web/supabase_schema.sql:18`). Whichever of these is actually installed live crashes on **any** `profiles` UPDATE, regardless of which columns are being changed — exactly matching the observed symptom when AIR-0224's fixture script tried to PATCH `referral_code`/`country_code`.

### Bug 2 — `handle_new_user()` not setting `referred_by`

Confirmed via a live, read-only Admin API check (`GET /auth/v1/admin/users/{id}`) that `user_metadata.referred_by_id` **was** correctly received and stored on `auth.users` for the AIR-0224 test accounts (e.g. User A's stored metadata included the real Default Sponsor UUID). So the bug isn't in the client/API layer — it's in what the `on_auth_user_created` → `handle_new_user()` trigger does with that value.

Two competing definitions of `handle_new_user()` exist in this repo's history:
- **Correct, current**: `auth-web/supabase_schema.sql:28-102`, `referred_by_id` fallback added by AIR-0122 (commit `18ea02a4`, 2026-07-03).
- **Old, broken**: root-level `MIGRATION.sql:16-23` — a "Picadiri Studio"-branded legacy bootstrap script (first committed `85c9f934`, 2026-02-01, five months before AIR-0122), whose `handle_new_user()` body is a trivial `INSERT INTO profiles (id, email, membership) VALUES (...)` that ignores `raw_user_meta_data` entirely.

Since `CREATE OR REPLACE FUNCTION` overwrites by name+signature regardless of source file, if `MIGRATION.sql`'s block was ever (re-)run against production after the correct version was deployed, it would silently replace the correct function — no change to the `on_auth_user_created` trigger attachment itself would be needed for this to happen. This matches the exact symptom observed and is consistent with the broader pattern already documented this project (`auth-web/supabase_schema.sql` repeatedly shown to drift from what's actually live — e.g. `profiles.is_superadmin` documented but absent, `migration_withdrawal_commission.sql` apparently never applied).

**Not independently confirmed** (would need `pg_proc` access this environment doesn't have) — `migrations/air_0224a_DIAGNOSTIC.sql` is provided as an optional read-only pre-flight check for whoever has SQL Editor access, but the hotfix itself doesn't depend on confirming this exactly, since re-asserting the known-correct function via `CREATE OR REPLACE` fixes it regardless of the precise prior mechanism.

## Hotfix design

`migrations/air_0224a_profile_referral_trigger_hotfix.sql`:
1. `DROP TRIGGER IF EXISTS` the 3 broken trigger *attachments* only (not the underlying functions — they may still be legitimately attached to other Gen 2/3 orphaned tables like `worker_jobs`/`commissions`, out of this hotfix's scope).
2. `CREATE OR REPLACE FUNCTION public.handle_new_user()`, verbatim from `auth-web/supabase_schema.sql:28-102`, plus re-asserting the `on_auth_user_created` trigger attachment (belt-and-suspenders — `CREATE OR REPLACE` alone doesn't require this, but costs nothing).
3. Backfill `referred_by` for the 4 known AIR-0224 E2E test accounts specifically (by email) — **not** a blanket fix for every `profiles` row with `NULL referred_by`, since `NULL` is legitimate for a real organic user with no referrer.
4. Self-verifying `DO` block (same pattern as every prior AIR-0221 apply script) — checks the 3 triggers are gone, `handle_new_user()`'s new body contains the `referred_by_id` logic, and the 4 test accounts' chain is now `DS ← A ← B ← C`. Any failure `RAISE EXCEPTION`s, aborting the transaction (the trailing `COMMIT` becomes a no-op).

`migrations/air_0224a_profile_referral_trigger_hotfix_rollback.sql`: restores the 3 trigger attachments exactly (verbatim `CREATE TRIGGER` from their source migrations) — but **honestly cannot** restore the exact prior `handle_new_user()` body (never directly observed) or would consider it harmful to try (that body was the bug). Does not revert the 4 test accounts' `referred_by` backfill by default (a commented block does, if truly wanted).

`migrations/air_0224a_DIAGNOSTIC.sql`: optional read-only pre-flight, for confirmation before applying — not a hard dependency.

## Existing policy on invalid/unmatched referrer values (documented per AIR-0224A's own request, not changed)

`handle_new_user()` **silently ignores** an invalid or non-matching `referred_by_id` — it does not reject the signup. An unparseable UUID is caught and treated as `NULL`; a well-formed UUID with no matching profile leaves the referrer unresolved, so `referred_by` is inserted as `NULL`. The signup always proceeds regardless. This is unchanged, pre-existing behavior. The one place a signup genuinely *is* rejected for a bad referral value is a **separate, earlier** check — `app/routers/auth.py`'s `validate_referral_code()` — which only applies to the referral-code text-entry flow (Scenario 4 in `REFERRAL_E2E_TEST_PLAN.md`), not the `referred_by_id` (Default Sponsor) flow this trigger handles.
